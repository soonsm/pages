이 값, JobParameters에 둘까 ExecutionContext에 둘까?

"이 값, 대체 어디에 넣어둬야 하지?"

Spring Batch에서 Job은 여러 Step이 순차적으로 실행된다. 앞 Step에서 값을 만들어 넣고 뒤 Step에서 꺼내 쓰다 보면, Step을 넘나들며 공유하는 값이 하나둘 늘어난다. 이 값들을 어디에 저장해둬야 하는지가 계속 걸렸다.

처음엔 단순하게 생각했다. "앞 Step에서 만든 값을 `ExecutionContext`에 넣고 뒤 Step에서 꺼내면 되겠지." 그런데 막상 짜보니 곳곳에서 기준이 필요했다.

-● 
어떤 값은 `JobParameters`에서 꺼내야 하고
-● 
어떤 값은 `ExecutionContext`에서 꺼내야 하고
-● 
Step마다 같은 값을 꺼내는 코드가 반복되고
-● 
앞 Step에서 넣은 값을 뒤 Step에서 읽는 코드도 반복된다

단순한 값 전달 문제가 아니었다. Job 실행 입력값과 Step 실행 결과를 어떻게 구분할 것인가의 문제였다.

## 1. 먼저 기준을 정했다

정리한 기준은 이렇다.

| 저장소 | 역할 |
| --- | --- |
| `JobParameters` | Job 실행 전에 외부에서 결정되는 입력값. Job 전체에서 변하지 않는다. |
| `StepExecutionContext` | 현재 Step 내부에서 사용하는 실행 상태. Step 재시작에 필요한 상태. |
| `JobExecutionContext` | 앞 Step에서 생성되어 뒤 Step으로 전달해야 하는 값. |

예를 들어 파일 처리 Job이라면 `JobParameters`에는 이런 값이 들어간다.

```
BASE_DATE
INPUT_FILE_PATH
FILE_NAME
FILE_SIZE
```

Job 실행 요청 시점에 이미 정해진 값이다. 특정 Step의 결과가 아니다.

반대로 첫 Step에서 파일 경로를 검증하고 실제 처리할 전체 경로를 만들었다면, 그 값은 `JobExecutionContext`로 넘긴다.

```
RESOLVED_FILE_PATH
PROCESSING_FILE_PATH
FILE_RECORD_ID
```

Job 시작 시점에는 없던 값이다. 앞 Step을 실행한 결과로 생긴 값이다.

기준은 이걸로 명확해졌다. **외부에서 들어온 입력값은 `JobParameters`에, 실행 중 생긴 Step 간 전달값은 `ExecutionContext`에 둔다.**

## 2. 왜 JobParameters를 ExecutionContext로 복사하지 않았나

잠깐 이런 생각이 들었다. "첫 Step에서 `JobParameters`를 통째로 `ExecutionContext`에 복사해두면, 뒤쪽 Step은 `ExecutionContext` 한 군데만 보면 되잖아?"

```
JobParameters
↓
ExecutionContext에 전부 복사
↓
뒤쪽 Step은 ExecutionContext만 사용
```

뒤쪽 Step은 단순해진다. 하지만 구조가 나빠진다고 봤다. 이유는 두 가지다.

첫째, 같은 값의 원본이 두 군데 생긴다.

```
JobParameters["FILE_NAME"]
JobExecutionContext["FILE_NAME"]
```

어느 쪽이 진짜 기준인지 애매해진다. 테스트에서도 한쪽만 채우고 다른 쪽을 빠뜨리기 쉽다. 재시작·재실행 상황에서는 더 헷갈린다.

**둘째, 더 근본적인 이유다. `JobParameters`와 `ExecutionContext`는 저장 위치만 다른 게 아니라 역할 자체가 다르다.** `JobParameters`는 `JobInstance`의 식별자를 결정한다. 같은 파라미터로는 같은 Job이 다시 실행되지 않는, Job의 정체성을 이루는 값이다. 반면 `ExecutionContext`는 실행 상태를 담는 저장소일 뿐 식별자가 아니다.

이 둘을 섞는 건 값 두 벌을 만드는 게 아니라 식별자와 상태라는 다른 책임을 뒤섞는 것이다. 당장은 편해도 나중에 발목을 잡는다. 그래서 `JobParameters`를 `ExecutionContext`로 복사하지 않기로 했다.

## 3. 그런데 왜 SpEL 주입이 아니라 유틸리티였나

`JobParameters`를 읽는 관용적인 방법으로 `@StepScope`와 SpEL late binding이 있다.

```java
@Value("#{jobParameters['FILE_NAME']}")
private String fileName;
```

알면서도 택하지 않았다. 이유는 두 가지다.

-● 
오타가 나기 쉽다. `"#{jobParameters['FILE_NAME']}"`는 전부 문자열이라 컴파일 타임에 걸러지지 않는다. key를 틀려도 실행해봐야 안다.
-● 
매번 같은 걸 타이핑해야 한다. Step이 늘어날수록 이 긴 표현식을 반복해서 쓴다.

무엇보다 내가 원한 건 값 하나를 주입받는 게 아니었다. 필수값 검증, 타입 변환, 관련 값의 DTO 묶음을 한곳에 모으고 싶었다. SpEL은 값을 꺼내줄 뿐 이걸 묶어주진 않는다. 그래서 유틸리티와 DTO 방식을 택했다.

정리하면 개선 방향은 이렇다.

1.1. 
`JobParameters`는 계속 `JobParameters`에서 읽는다. (복사하지 않는다)
2.2. 
앞 Step에서 생성한 값만 `ExecutionContext`로 전달한다.
3.3. 
매 Step마다 반복되는 코드는 유틸리티로 감싼다.

책임은 유지하되 사용 코드는 줄이는 방향이다.

## 4. JobParameters 중복 제거

Step마다 이런 코드가 반복됐다.

```java
String baseDate = jobParameters.getString(BASE_DATE);
String inputFilePath = jobParameters.getString(INPUT_FILE_PATH);
String fileName = jobParameters.getString(FILE_NAME);
Long fileSize = jobParameters.getLong(FILE_SIZE);
```

그래서 필요한 값을 꺼내 DTO로 변환하는 유틸리티를 만들었다.

```java
public record FileJobParameters(
String baseDate,
String inputFilePath,
String fileName,
long fileSize
) {
}
```

```java
public final class FileJobParametersUtils {

private FileJobParametersUtils() {
}

public static FileJobParameters from(StepExecution stepExecution) {
return from(stepExecution.getJobParameters());
}

public static FileJobParameters from(JobParameters jobParameters) {
return new FileJobParameters(
requireString(jobParameters, BASE_DATE),
requireString(jobParameters, INPUT_FILE_PATH),
requireString(jobParameters, FILE_NAME),
requireLong(jobParameters, FILE_SIZE)
);
}

private static String requireString(JobParameters jobParameters, String key) {
String value = jobParameters.getString(key);
if (value == null || value.isBlank()) {
throw new IllegalArgumentException("필수 JobParameter가 없습니다. key=" + key);
}
return value;
}

private static long requireLong(JobParameters jobParameters, String key) {
Long value = jobParameters.getLong(key);
if (value == null) {
throw new IllegalArgumentException("필수 JobParameter가 없습니다. key=" + key);
}
return value;
}
}
```

>
`StepExecution#getJobParameters()`는 Spring Batch 5.x에서 직접 제공된다. `getJobExecution().getJobParameters()`를 거칠 필요가 없다.

이제 Step에서는 한 줄이면 된다.

```java
FileJobParameters parameters = FileJobParametersUtils.from(stepExecution);
```

장점은 이렇다.

-● 
문자열 key 중복 제거
-● 
타입 변환 코드 중복 제거
-● 
필수값 누락 처리 통일
-● 
Step 코드가 업무 로직에 집중

한 가지 짚어둘 게 있다. `FileJobParameters`에서 파일 경로를 바로 `Path`로 바꾸지 않았다. `INPUT_FILE_PATH`는 JobParameter 상으로는 `String`이다. `Path.of()` 변환, 존재 여부·읽기 권한·크기 검증은 첫 Step에서 하는 게 더 명확하다고 봤다. DTO는 입력값을 담기만 하고, 파일 시스템 검증은 Preparation Step의 책임으로 분리했다.

## 5. ExecutionContext 중복 제거

다음은 Step 간 값 전달이었다.

Step 실행 중 만든 값은 바로 `JobExecutionContext`에 넣기보다, 먼저 `StepExecutionContext`에 넣고 `ExecutionContextPromotionListener`로 `JobExecutionContext`에 승격하는 게 적절하다.

```
앞 Step
↓
StepExecutionContext에 값 저장
↓
PromotionListener가 JobExecutionContext로 승격 (Step이 정상 완료된 경우)
↓
뒤 Step에서 JobExecutionContext 값 조회
```

하나 짚어둘 게 있다. `ExecutionContextPromotionListener`는 기본적으로 **Step의 ExitStatus가 `COMPLETED`일 때만 승격**한다. 실패한 Step의 중간 값은 승격되지 않는다. `setStrict(true)`는 승격 대상 key가 StepExecutionContext에 없으면 예외를 던진다는 뜻이지, 승격 조건과는 별개다. 이 둘을 헷갈리면 재시작 동작을 잘못 이해하기 쉽다.

이 코드도 반복된다.

```java
stepExecution.getExecutionContext()
.putString(RESOLVED_FILE_PATH, resolvedFilePath.toString());

stepExecution.getJobExecution()
.getExecutionContext()
.getString(RESOLVED_FILE_PATH);
```

그래서 ExecutionContext용 유틸리티를 만들었다.

```java
public final class BatchExecutionContextUtils {

private BatchExecutionContextUtils() {
}

public static void putStringToStep(StepExecution stepExecution, String key, String value) {
stepExecution.getExecutionContext().putString(key, value);
}

public static void putLongToStep(StepExecution stepExecution, String key, long value) {
stepExecution.getExecutionContext().putLong(key, value);
}

public static String requireStringFromJob(StepExecution stepExecution, String key) {
String value = stepExecution.getJobExecution()
.getExecutionContext()
.getString(key);
if (value == null || value.isBlank()) {
throw new IllegalArgumentException("필수 JobExecutionContext 값이 없습니다. key=" + key);
}
return value;
}

public static long requireLongFromJob(StepExecution stepExecution, String key) {
ExecutionContext context = stepExecution.getJobExecution().getExecutionContext();
if (!context.containsKey(key)) {
throw new IllegalArgumentException("필수 JobExecutionContext 값이 없습니다. key=" + key);
}
return context.getLong(key);
}

public static ExecutionContextPromotionListener promotionListener(String... keys) {
ExecutionContextPromotionListener listener = new ExecutionContextPromotionListener();
listener.setKeys(keys);
listener.setStrict(true);
return listener;
}
}
```

앞 Step에서는 이렇게 쓴다.

```java
BatchExecutionContextUtils.putStringToStep(
stepExecution,
RESOLVED_FILE_PATH,
resolvedFilePath.toString()
);
```

Step 설정에서는 Listener를 등록한다.

```java
@Bean
public ExecutionContextPromotionListener filePreparationPromotionListener() {
return BatchExecutionContextUtils.promotionListener(RESOLVED_FILE_PATH);
}
```

뒤 Step에서는 이렇게 꺼낸다.

```java
String resolvedFilePath = BatchExecutionContextUtils.requireStringFromJob(
stepExecution,
RESOLVED_FILE_PATH
);
```

Step 코드에서 Spring Batch 내부 API를 직접 다루는 부분이 줄었다.

## 6. 개선 후 코드의 모습

개선 전에는 Step 코드가 이런 형태가 되기 쉬웠다.

```java
JobParameters jobParameters = stepExecution.getJobParameters();
String fileName = jobParameters.getString(FILE_NAME);
String inputFilePath = jobParameters.getString(INPUT_FILE_PATH);
String resolvedFilePath = stepExecution.getJobExecution()
.getExecutionContext()
.getString(RESOLVED_FILE_PATH);
```

개선 후에는 이렇게 바뀐다.

```java
FileJobParameters parameters = FileJobParametersUtils.from(stepExecution);

String resolvedFilePath = BatchExecutionContextUtils.requireStringFromJob(
stepExecution,
RESOLVED_FILE_PATH
);
```

줄 수가 준 것보다 중요한 건 의미가 명확해졌다는 점이다.

-● 
`FileJobParameters` → Job 실행 입력값
-● 
`requireStringFromJob(...)` → 앞 Step이 생성한 전달값

값의 출처가 코드에 드러난다.

## 7. 결론

`JobParameters`와 `ExecutionContext`는 둘 다 Step에서 꺼내 쓸 수 있어 쉽게 섞인다. 하지만 역할은 다르다. `JobParameters`는 Job의 정체성을 이루는 입력값이고, `ExecutionContext`는 실행 상태와 Step 간 전달값이다.

그래서 이렇게 정리했다.

-● 
외부 입력값은 `JobParameters`에 둔다.
-● 
실행 중 생성된 값은 `ExecutionContext`에 둔다.
-● 
`JobParameters`는 `ExecutionContext`로 복사하지 않는다.
-● 
반복 코드는 유틸리티와 DTO로 제거한다.

Step 코드는 단순해지고 값의 출처는 명확해진다.

결국 중요한 건 "어디서든 꺼내 쓸 수 있게 만드는 것"이 아니라 "이 값이 왜 여기 있는지 설명할 수 있는 구조를 만드는 것"이었다.
